# Real-node verification checklist

Claims from roadmap v5 (`6785f77..7d3d346`) that rest on code reading and hermetic tests only — no physical homelab or Android device was reachable while they were built. Items stay open until confirmed on hardware; strike one (with the date and the node/OS) when verified.

## Update scans (Phase 3B)

- [x] apt / dnf / checkupdates / apk probes and parsers against real distros — 2026-11-27, by running the app's own scripts: Linux Mint 22.2 and Debian 12 (apt: `Listing...` without ` Done`, 44 and 4 real rows, an empty listing after an upgrade), Fedora 45 with dnf5 (rows under an `Upgrades` heading, exit 100 = updates, some rows padded with single spaces, nothing printed and exit 0 when current), Arch Linux with pacman-contrib (`checkupdates` exit 0 = updates, 2 = current, 1 = a real error such as a missing `fakeroot`), Alpine 3.24.4 (`apk version -l '<'` prints an `Installed:/Available:` banner and bare `version-rN` on the available side). Three parser bugs fell out of the real output and are fixed: dnf rows split on aligned columns only, the apk available side was read as `name-version`, and `checkupdates` exit 1 was treated as "up to date". The REAL captures are the fixtures of `OsUpdateScanTest`
- [x] The package-index refresh needs root on apt and apk — 2026-11-27: unprivileged `apt-get update` exits 100 (Debian 12) and `apk update` exits 99 (Alpine 3.24.4), which used to leave a scan silently on a stale index; the refresh now runs over the node's privilege path and a listing without it is reported `STALE`. A refresh that exits 0 is not automatically trusted either: real Debian 12 shows `apt-get update` exiting 0 with `W: Failed to fetch …` / `W: Some index files failed to download` when one repository is unreachable or its TLS chain untrusted — that reads as `STALE — Package index only partly refreshed`. The same day, dnf5 (Fedora 45) turned out to skip a dead repository silently and still exit 0; the listing script now sets `--setopt='*.skip_if_unavailable=False'`, which both dnf5 and dnf 4.14 (Rocky 9) accept, so an unreachable repository fails the listing loudly (dnf4 exit 1 with the reason on stderr, dnf5 exit 1 once the option is set)
- [x] Failure wordings captured from real failure states — 2026-11-27, driving real distros into each state and keeping the node's own words: sudo 1.9.13p3 (no-tty without `-S`: `sudo: a terminal is required to read the password…`; sudoers `requiretty`: `sudo: sorry, you must have a tty to run sudo`; a user outside sudoers: `nosudo is not in the sudoers file.`; sudo not installed: bash `sudo: command not found`, dash `sudo: not found`), apt 2.6.1 (lock really held: `E: Could not get lock /var/lib/apt/lists/lock. It is held by process 2655 (perl)` / `E: Unable to acquire the dpkg frontend lock …, is another process using it?`; unsigned repository: `NO_PUBKEY …` / `is not signed`, exit 100; removed release: `does not have a Release file`, exit 100), dnf 4.14 apply under a really held rpm lock (`RPM: error: can't create transaction lock …` — dnf5's apply has no lock wording at all, only `Transaction failed: Rpm transaction failed.`), pacman apply under a really held db lock (`error: failed to init transaction (unable to lock database)`), apk (`WARNING: updating and opening …: DNS lookup error`, exit 2, unreachable; `ERROR: Unable to lock database: Permission denied`, exit 99, unprivileged), Arch (`==> ERROR: Cannot fetch updates`, exit 1, unreachable mirror; `Cannot find the fakeroot binary`, exit 1). All live as REAL fixtures in `OsUpdateScanTest`
- [x] Reboot-recommendation probe output — 2026-11-27: `REBOOT_REQUIRED=0` and `=1` (with `/var/run/reboot-required` present) + `__NR_EXIT__=skip` captured on Debian 12; the script's shape confirmed on Fedora 45, Rocky 9.9 and Arch (none of which ships `needs-restarting` — the probe reports "skip"). The `needs-restarting -r` exit-1 branch itself stays unverified
- [x] apt apply against a really held dpkg lock — 2026-11-27, Debian 12, a real fcntl holder on `/var/lib/dpkg/lock-frontend`: `DPkg::Lock::Timeout` makes apt wait (`Waiting for cache lock: … held by process NNN (perl)...` on stdout, repeatedly) and it completes once the holder exits; an exhausted budget fails with exit 100, the holder named on stdout and `E: Unable to acquire the dpkg frontend lock …` on stderr — the failure diagnosis names the holder from either stream
- [x] On-device scan + apply end to end from the Android transport — 2026-11-27, the app itself on a POCO F1 (LineageOS, wireless adb) over WiFi against a Debian 12 sshd node: TOFU fingerprint dialog, password auth, both sudo paths (a passwordless-sudo user and a sudo-password user via `sudo -S -p ''` with the login password read from the vault), the Rack updates card ("1 OS · 0 containers"), the pending-updates sheet with the package row, hold-to-confirm applies (real apt transactions, verified in the node's dpkg database) and the audit ledger entries for scan, apply and a refused hold (BLOCKED · 0ms), chain verified. Two notes from the same session: the scan ledger encodes its outcome as exit 0 / −1 by construction (SUCCESS → 0, anything else −1), so "EXIT -1" on a scan entry means "not fully successful" — read the snippet for why, it is not a transport failure; and two node entries pointing at one machine contend for the apt lists lock (`DPkg::Lock::Timeout` covers dpkg locks only — a contended lists lock fails fast, exit 100), which demotes that scan to STALE with the diagnosis; distinct real nodes do not contend
- [ ] KNOWN LIMITATION (tool behaviour, no app-side fix): Arch `checkupdates` under a held pacman db lock exits 2 with no output — indistinguishable from "up to date" (the apply path does name the lock). Conversely a held rpm lock does not block `dnf check-update` at all — it is read-only; the lock bites on apply only
- [ ] Privileged OS apply on a real apt node: conffile conflicts under `--force-confdef --force-confold`, and it never reboots — the apply command itself ran to exit 0 as an unprivileged user through `sudo -n` on a Debian 12 container (four packages upgraded, no reboot); the lock-timeout behaviour was verified 2026-11-27 against a real lock; conffile conflicts were not exercised
- [x] buildx index-digest comparison: match / mismatch verdicts on the classic store — 2026-11-27, Docker Engine 29.10 with the `overlay2` store: a local `RepoDigests` equal to the registry's index digest reads `UP_TO_DATE` (`linuxserver/radarr`, `jellyfin/jellyfin`), a different one `UPDATE_AVAILABLE` (`lscr.io/linuxserver/lidarr:latest`); a Docker Hub `429` (anonymous pull budget spent) and a gcr.io token refusal leave the image `UNKNOWN` with the registry's words in the report. The batch script ran under bash, dash and sh with identical records; 25 references took about 27 s in waves of six, against 88 s sequentially
- [x] `manifest inspect -v` fallback interpretation — 2026-11-27, same host: the full image ids of current images appear verbatim as remote config digests (`linuxserver/radarr`, `jellyfin/jellyfin`), an outdated image's does not (`lidarr`), and a refused lookup exits 1 with no output at all, so a partial list cannot be read as "update available". Found on the way: the default `docker images` listing prints 12-character ids, which can never equal a 64-hex digest — the scan now lists with `--no-trunc` and refuses to decide on a truncated id
- [ ] PINNED / LOCAL verdicts on the classic store — the host used above had no digest-pinned container and no locally built image behind a running container

## SSH transport (Phases 1A/1B/2)

- [ ] Host key: TOFU accepted and persisted on first connect; a changed key rejected before any auth data is sent
- [x] Privileged sudo flows against a real sshd — 2026-11-27, Debian 12 container running sshd, driven with the app's own JSch exec and stream logic replayed from the JVM: a genuinely passwordless user succeeds in every privilege mode (root, `sudo -n`, `sudo -S -p ''`), `sudo -S -p ''` with a wrong password prints `Sorry, try again.` / `sudo: no password was provided` / `sudo: 1 incorrect password attempt` and never echoes what it read, and `sudo -n` without the right prints `sudo: a password is required`. Extended the same day with the remaining sudoers states, each captured from that real state: sudoers `requiretty` (`sudo: sorry, you must have a tty to run sudo`), `sudo` without `-S` and without a terminal (`sudo: a terminal is required to read the password…`), a user outside sudoers (`nosudo is not in the sudoers file.`), and sudo not installed (bash `sudo: command not found`, dash `sudo: not found`, exit 127). The failure diagnosis and the scan's STALE reason are worded against that output. The probe cache is keyed by node and login user, so a node whose SSH user changes is probed again
- [ ] The same flows from the Android app's own transport on a phone, against the user's Raspberry Pi and Mint nodes — the phone side itself is confirmed (see the on-device scan + apply item above); what stays open is the user's actual Pi and Mint hardware
- [ ] Two unreachable nodes must not push a healthy node behind them to OFFLINE (per-server connect mutex, ~16 s worst-case hold)
- [ ] Test SSH with transient credentials writes nothing to the vault
